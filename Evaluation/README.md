# Day16 基准题集与评分口径

`ResearchSuiteV1.json` 是后续评估的固定输入，不是已测出的成绩。共 15 条：4 条文档检索引用、7 条工具选择、4 条合成价格数值。变更标签或容差时应升级 `version`，保留旧版用于前后对比，不能根据一次失败悄悄修改标准答案。

## 来源与可运行性

- 文档题引用已有的 `GoldenQuestionsV1.json`。原样例依赖单独提供的两页公开披露 PDF；仓库中的题目文本不等于已取得原文。只有确认 PDF 内容、页码、解析结果和知识库归属后才能报告真实检索指标。没有文档时标为“未运行”，不能把模拟命中当作 Recall。
- 工具题是明确标记的合成问题，不声称来自真实客户。可离线核对意图、工具集合和缺失输入限制。
- 数值题是合成价格序列。预期结果的 `calculation_note` 给出人工复核方法；价格是序列，不自动冒充真实交易日收盘价。

## 预定评分规则

| 类别 | 主指标 | 分母与通过条件 |
| --- | --- | --- |
| 文档检索 | Recall@20、精排命中@5 | 只计有可验证来源且应能回答的题；文档缺失时该类不计算。内容片段与页码均须吻合。拒答题单独算拒答准确率。 |
| 工具选择 | 意图准确率、工具集合完全匹配率、限制识别率 | 7 条工具题全计；多工具题需集合完全一致，不能“碰巧命中一个”就算通过。无价格风险题必须指出缺失输入。 |
| 数值一致性 | 指标通过率、整题通过率 | 以每条 `expected_metrics` 为分母；`abs(actual - expected) <= absolute_tolerance`。一题全部已标指标通过才算整题通过；不得把 VaR 与 CVaR、累计收益与最大回撤混为一项。 |

评分应输出题集版本、可运行/不可运行数量、失败编号和原因。不可运行不能算通过，也不能悄悄从分母删掉；应单列“覆盖率”。性能耗时与用量属于后续步骤，不能用本题集文件推断 P95 或成本。

## Step2 文档检索评估的运行边界

运行 `uv run python -m finsight.workers.evaluate_retrieval` 会输出 `status: not_run`、空指标和四个未运行题号；这是当前没有原 PDF 与完整检索观察结果时的正确状态。命令可用 `--observations <JSON路径>` 读取完整的 `EvaluationObservation` 数组，但这只表示“对提供的观察结果评分”，不自动证明观察结果来自真实 PDF。真实流水线仍须走需要 PostgreSQL、文档解析、向量库、嵌入与精排器的显式集成验收，并保存源文档版本与运行条件。

本步评分按三个有证据题作 Recall@20 与精排命中@5 的分母，拒答题单独计拒答准确率；MRR 让靠前的相关证据得到更高分。引用正确率还要求被引用的那段证据位于精排 Top-5，并且正文片段和页码符合题目标准。逐题报告会标出 `retrieval_miss`、`rerank_miss`、`citation_not_supported` 或 `unexpected_refusal`，避免一个总分掩盖故障阶段。

## Step3 工具与数值基线

运行 `uv run python -m finsight.workers.evaluate_research` 会调用当前规划器和确定性风险计算器，对 7 条工具题、4 条数值题作离线评估。报告明确标记 `source: synthetic_fixture`，逐题输出意图、工具集合、缺失输入限制是否正确，以及各指标的预期值、实际值、绝对误差和通过状态。

工具集合按**完整集合**比较；意图准确率、工具集合准确率和限制识别准确率分别以 7 题为分母。整题通过必须三项均正确。数值按 17 个预先标注的指标逐项比较，`abs(actual - expected) <= absolute_tolerance` 才通过；一题全部指标通过才计为数值整题通过。缺失指标、非有限值和超容差均为失败；观察值缺题、重复题或多出题则整次评估拒绝，不计算好看的局部平均。

这组结果只证明当前**规划选择**与**合成价格上的公式实现**符合固定样例。它没有运行文档检索、数据库查询或真实工具故障恢复，也不代表实际研究完成率、历史风险模型的统计有效性或真实市场表现。

## Step4 本地结构化执行轨迹

请求中间件生成并返回 `X-Request-ID`；同一次请求的规划、工具执行、研究完成与 HTTP 完成事件共用该编号。人工复核是后续独立请求，因此用 `thread_id` 关联研究与复核，不能误称它们拥有同一个请求编号。日志只输出严格字段白名单中的路由模板、状态、耗时、工具名称及错误代码等元数据，不记录提问原文、价格序列、检索材料、令牌或复核备注。

日志默认写到本地标准输出，属于排障轨迹，不替代现有操作审计。外部观测平台尚未启用，不能声称已上传轨迹、统计费用或完成生产监控。

## Step5 本地运行指标

把 Step4 的纯轨迹 JSON 行保存为一个 UTF-8 JSONL 文件后，可运行 `uv run python -m finsight.workers.report_runtime_metrics --input <JSONL路径>` 输出聚合报告。输入必须是结构化轨迹事件，每行一个 JSON；未知字段、损坏行和同一请求重复的 HTTP 完成事件会被拒绝。报告不回显原始输入行。

HTTP 请求数只以 `http_completed` 为分母，5xx 比例为 `5xx / HTTP请求数`；4xx 单列，因为认证拒绝或参数错误不能直接当作服务端故障。研究回答状态只以 `research_completed` 为分母；`insufficient_evidence` 是谨慎不回答，不等同于 5xx。工具的成功、不可用和失败按 `tool_completed` 的实际执行次数统计，按工具名称拆开。缺少 HTTP 完成事件的请求编号单列为不完整，不能算成功。空样本的比率和耗时分位数为 `null`，不伪造 0%。

P50/P95 使用最近秩法对已观察耗时计算，只是对当前样本的描述。没有固定负载、样本量、机器条件和外部依赖状态时，不能称为性能基线。令牌用量与费用目前没有可信采集源，字段为 `null`，不能把本地模型或其他工具的调用数换算成费用。Step6 再在固定条件下做性能验收。

## Step6 本地性能基线与验收边界

运行 `uv run python -m finsight.workers.day16_acceptance` 会先用同一版题集核对合成工具与数值题，再用默认 5 轮预热、100 轮测量，顺序执行每轮 7 条规划与 4 条风险计算。报告包含题集版本、Python/操作系统/架构、样本数、规划和风险计算各自的 P50/P95/最大耗时。可用 `--warmups` 和 `--rounds` 显式改变运行次数；比较前须保持配置、机器和环境一致。

这个结果是**单进程离线微基线**，不是 HTTP 请求端到端延迟或并发吞吐。它不启动外部服务、不占端口，也不测数据库、PDF 解析、向量检索、精排或人工复核链路。报告的 `api_latency` 为 `null`；外部文档题仍是 `not_run`。合成题全过时状态仍为 `local_pass_partial_coverage`，只有本地题失败才是 `local_failed`，不能把部分覆盖写成完整平台验收。真实端到端验收仍需提供原 PDF、服务依赖和固定负载条件。

## 金融口径

本项目历史 VaR 表示正的单期潜在损失；历史 CVaR 表示超过 VaR 阈值的尾部损失均值。最大回撤是从此前峰值到谷值的跌幅，而不是期末收益率。例如 `[100, 90, 99]` 的累计收益率是 −1%，最大回撤仍是 −10%。数值题的容差仅处理浮点表示误差，不放宽错误的金融口径。

这些三点价格序列只有两期收益率，适合检查公式与边界，不足以估计可用于投资决策的真实 95% VaR。真实风险评估还需要足够长、来源可信且口径一致的历史序列。
